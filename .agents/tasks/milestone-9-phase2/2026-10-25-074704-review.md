# 3-level frozen cascade, level-1 training path and `--min-pairs` (milestone 9 phase 2)

Phase 2 makes level 1 trainable as the third stage of a frozen 4 -> 2 cascade. `models.cascade.FrozenChain` restores both frozen stages from one milestone-8 level-2 checkpoint (`model` + `frozen_stage`, level-4 fingerprint checked against the m8 `cascade.fingerprint`). The trainable level-1 model has the identical default ModelConfig and copies the level-2 weights. The Trainer picks the chain branches with a trace-time `n_stages` switch. Also added: an opt-in `--min-pairs n` floor for the linear and deform pair losses, `val_<set>_frozen4` baselines, `val/wall_s`, per-stage provenance and resume checks, `slurm/m9_level1_cascade.sh`, and checker / memory-tool extensions. Defaults stay bit-identical (goldens max |diff| 0, 520-test suite OK).

Watch for: the checker's `INFO step_time` projection, which the script header and the report use to set the long run's `--time`, counts validations at the smoke run's `val_every` (100), not the long run's 500. It projects 80 validation passes instead of the design's 16 (**confirmed**, MEDIUM).

**Verdict**: NEEDS_CHANGES (CHANGES_REQUESTED: 0 HIGH, 1 MEDIUM, 1 NIT)

## High-level view

The chain is the phase-1 stand-in's math with real weights. `FrozenChain._linear` / `_deform` pool to level 2, run frozen level 4, pre-warp, run frozen level 2 in eval mode, compose at level 2, and upsample. T-C2 shows identical outputs to `FrozenChainStandIn` (max |diff| 0), so the phase-1 memory measurements apply. Every restore failure in `from_checkpoint` leaves as ValueError, and main turns it into a `SystemExit("main.py: --cascade-from ...")`. The design-review NITs 1-3 (`_build_frozen_model(cfg, level=...)`, `_load_cascade_source(..., level=2)`, the `deform_group_size` comment) are applied.

Trainer dispatch is a Python int fixed at construction (`self._n_stages`; getattr default 1). The level-2 path keeps its exact branch, and the chain gets a separate `elif`. Skip at level 1 is `CS.skip_to(skip, A4/U4, chain)` and is built only for p > 0. Validation stores dict-valued frozen outputs for the chain and emits `_frozen` (4 + 2) and `_frozen4` (level 4 alone) from one cached pass. `val/wall_s` is added only at level 1.

`--min-pairs n` sets k = min(max(N, round(p N(N-1))), N(N-1)). At k == N it uses a `tf.cond` cycle branch under `name_scope("min_pairs")` and keeps the single uniform draw, and the `"1"` path returns before any new op. I re-ran the mirror check myself: `postprocess.num_pairs`, `memory_model.num_pairs` and the checker's `expected_pairs` agree for N 2-40, p ∈ {0.05, 0.1, 0.25, 1}, both modes. Also confirmed: one N-cycle for N 2/3/4/5/8/11, distinct non-self pairs for N 12/16, and equal generator state after `"1"` vs `"n"`.

The SLURM script follows the cluster rules: `-A qtim`, rtx8000, `--gpus=1`, `-N 1`, one task, 3 CPUs, 64G, logs in the project folder, and no `entre`. It passes no width flags, so `check_cascade_config` stays strict against m8's stored config. It has a resume-safe `CASCADE_FROM` guard and integer / choice validation of the env knobs. The checker additions default off. Its one defect is the time projection: it projects validation passes with the wrong `val_every`.

### Long-run `--time` projection counts validations at the smoke's cadence

Design §8 sets the long-run time from the smoke as T = 1.3 × (8000 × s_mean + **16** × s_val + s_recal), printed by `check_mixed_run.py --project-steps 8000`. `_step_time` takes the cadence from the analysed run's own config:

```python
val_every = args.get("val_every")                      # smoke: 100
n_val = project_steps / float(val_every) if ...        # 8000 / 100 = 80, not 16
```

The smoke submit line sets `VAL_EVERY=100`, so the printed projection adds 64 extra validation passes. At the design's ~300 s per pass that is about +7 h (×1.3), on a ~35 h estimate. The error is on the safe side (over-request), but it inflates the number used for the `--time` and A100 decision and can push it past the 48 h default. The line shows "80 val", so a careful reader can correct it by hand. The unit test fixture uses `val_every` 10 and asserts the 800-pass arithmetic, so it encodes the same behaviour. Fix: a `--project-val-every` option (the script passes 500, or `VAL_EVERY_LONG`), falling back to the run's `val_every`.

### Coverage of the deform chain end to end

T-E1 (the scripted level 4 -> 2 -> 1 + resume chain) trains rigid only, with AMP + split. The local GTX 1080 cannot fit a level-1 deform step (documented deviation 2). `train_deform/n_pairs`, `val_deform_frozen4/*`, `ckpt/best_deform` and the deform PNG are therefore not exercised end to end before the cluster. Unit tests cover the deform branches: T-C2 outputs, T-C6 skip graph / eager, T-V1 `_frozen` / `_frozen4` from the chain fields. The checker's deform paths are covered by fake run dirs. The smoke run's checker asserts all of these (`--expect-cascade-stages 2 --expect-min-pairs n`), so it is the first real end-to-end deform test and should be read as such.

### Measurement records after the dispatch change

With `n_stages = 2` on `FrozenChainStandIn`, `measure_level_memory.py --level 1 --cascade true --val-pass true` now runs the Trainer's chain branches. In eval mode it also returns U4 / U4_inv / V4 (3 × N × ~83 MB at level 1 plus upsample temporaries). The design wants this, because the measurement matches the real run. But new `val_peak_mb` values are about 1 GB above a like-for-like rerun of job 10516237's configuration, while the docstrings still call the records comparable (NIT 2).
